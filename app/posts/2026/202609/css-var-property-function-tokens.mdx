## はじめに

- 前回の記事（[[think-about-calc.mdx]] / [[astryx-design-tokens.mdx]]）からの流れを一言で
  - calc()の基礎とCSS値解決プロセスは前回扱った
  - Astryx記事の結論「優れたトークン設計は値の一覧表ではなく、少数パラメータからの生成ルール」を、ビルドツール（StyleX）なしでネイティブCSSだけで再現できないか、という動機
- 出発点になった素朴な疑問を紹介
  - `--spacing-1: 4px` のようなトークンを `--unit: 4` + `calc()` で導出しようとしたら「トークン文字列なのにcalcの引数型と合うの？」と引っかかった、という実体験ベースの導入

## var()の正体：カスタムプロパティは「型を持たないトークン列」

- カスタムプロパティは `<declaration-value>`（ほぼ任意のトークン列）として定義され、var()は型変換ではなく生トークンの置換であることを説明
- Cプリプロセッサのマクロ置換に例える（一度きりの静的展開ではなく、computed-value timeに毎回解決される点が違う、という注記も）
- 実験1: `--unit: 0.0025rem` を `calc(var(--unit) * 400)` で使うと素直に`16px`になる
- 実験2: `--unit: abc` のような不正値を代入しても代入時にはエラーにならず、calc()で消費された瞬間にそのプロパティだけがIACVT（invalid at computed-value time）になり、`width: auto`にフォールバックする（＝原因箇所から離れた場所で静かに壊れる）
- 「型がないから緩い」のではなく「型という概念自体がなく、消費される瞬間まで検査が先送りされる」という結論

## @propertyで型を宣言する本当の意味

- よくある説明（バリデーション・IDE補完）は副次的な効果にすぎない、という切り口
- 実験3: `syntax: '<number>'` で登録した`--unit-typed`に不正値`abc`を代入すると、代入した瞬間に`initial-value`へフォールバックする（＝検査タイミングが「消費時」から「代入時」に前倒しされる）
- 型の本質はアニメーション補間: Web Animations APIで無登録プロパティと`<number>`登録プロパティを同条件でアニメーションさせ、25%/50%/75%地点をサンプリング
  - 無登録: 0px→100pxが50%地点で瞬間的にジャンプ（discrete補間）
  - 型登録: 25px/50px/75pxと線形に補間される
  - `<color>`ならLab/OKLab空間での補間、`<transform-list>`なら行列分解、など型ごとに補間アルゴリズムが変わる点にも触れる
- スペーシングトークンの文脈での実用判断：静的な値の計算だけなら型登録は不要、ホバーなどで`transition`させたい対象だけ選択的に型登録する

## @functionでプリミティブ層を式に畳み込む

- CSS Functions and Mixins Module（`@function`）の紹介、Chromiumでの動作確認（バージョン・検証時点を明記）
- `--unit` + `@function --spacing(--n) { result: calc(var(--n) * var(--unit)); }` の実装例
- 実験4: `--spacing(1.5)`のような小数倍率も計算でき、`calc(--spacing(2) + 10px)`のように他のcalc式とも合成できる
- 実験5（重要）: `@function`は静的展開されるSassの`@function`とは違い、**呼び出し元のカスケード値**を見にいく（動的スコープ）
  - `--unit`をローカルに上書きした要素で`--spacing(2)`を呼ぶと、上書き後の値がそのまま反映される
  - これはJS的な「クロージャで定義時の値を覚える」関数とは逆の性質、という比較

## Semantic層はどう変わるか

- 「spacing-1〜spacing-20を全部用意しても使うか分からない」という設計上の疑問
- このブログのdesign-system.md自体が「Primitiveは直接参照せず、Semantic層を経由する」と定めていることを紹介し、プリミティブ層はそもそも公開APIではないという整合性の話
- Before/After比較
  - Before: `--size-*`を数十個列挙 → 使われない値も生まれる
  - After: `--unit` + `@function`だけを持ち、Semantic層が必要な倍率だけをその場で計算する
- トレードオフも正直に書く: 列挙型プリミティブが担っていた「一覧性・ドキュメント性」が失われる点、Semantic層のgrepで代替できる範囲かどうか

## ブラウザ対応と導入の現実解

- `@function`はまだ新しい仕様。執筆時点でのブラウザ対応状況を書く前にcaniuse等で要確認、という注記
- 実務投入するなら、`@supports`でのフォールバックやビルド時の静的展開（PostCSS等）と並走させる案を提示
- このブログ自体（HonoX + Vite）に導入するかどうかは別途判断、というスコープの区切り

## まとめ

- var()は型を持たないトークン置換、@propertyは型による安全性というより「補間のためのレシピ」、@functionはSemantic層だけを起点に値を動的生成する仕組み——という3段の理解の積み上げを一文でまとめる
- Astryx記事の結論（生成ルールとしてのトークン設計）が、ビルドツールなしのネイティブCSSでもかなりの部分まで実現できる、という着地
